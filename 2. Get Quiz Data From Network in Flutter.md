# QuizApp (Flutter)

Objective: Learn To Get A Quiz Data From Network

Prerequisites
This project is for users who have completed the Flutter QuizApp built with `setState`, `Form`, and `Navigator` (see [wakinochien/quiz_app](https://github.com/wakinochien/quiz_app)).

This is the Flutter counterpart to [2. Get Quiz Data From Network.md](2.%20Get%20Quiz%20Data%20From%20Network.md) (the native Android/Kotlin version, built with Retrofit + Moshi + ViewModel/LiveData). Flutter doesn't need a separate networking library, JSON codegen library, or a ViewModel/LiveData layer — `package:http` plus Dart's built-in `dart:convert` and `FutureBuilder` cover the same ground with far fewer moving parts. Where useful, each step below notes its Android equivalent.

#### Step 1: Add the `http` package ####
- Equivalent to adding Retrofit to `build.gradle` (Android Steps 1–2).
- Run:
  ```bash
  flutter pub add http
  ```
- This adds `http: ^1.6.0` under `dependencies:` in `pubspec.yaml`. No Java-8/Kotlin build-option changes are needed (Android Step 3 has no Flutter equivalent).

#### Step 2: Update the `QuizQuestion` model to match the API response ####
- Equivalent to the `Question` data class with `@Json(name = ...)` annotations (Android Steps 13).
- `lib/models/quiz_questions.dart` was changed from a single `answers` list (with the correct answer hardcoded at index 0) to explicit `correctAnswer` / `incorrectAnswers` fields, since a real API response doesn't guarantee ordering:
  ```dart
  class QuizQuestion {
    const QuizQuestion({
      required this.text,
      required this.correctAnswer,
      required this.incorrectAnswers,
    });

    final String text;
    final String correctAnswer;
    final List<String> incorrectAnswers;

    List<String> get shuffledAnswers {
      final answers = [correctAnswer, ...incorrectAnswers];
      answers.shuffle();
      return answers;
    }
  }
  ```
- A `fromJson` factory constructor maps the raw JSON keys (`question`, `correct_answer`, `incorrect_answers`) onto the typed fields — this is Flutter's equivalent of Moshi's `@Json(name = "correct_answer")` mapping, just written by hand instead of generated:
  ```dart
  factory QuizQuestion.fromJson(Map<String, dynamic> json) {
    return QuizQuestion(
      text: Uri.decodeComponent(json['question'] as String),
      correctAnswer: Uri.decodeComponent(json['correct_answer'] as String),
      incorrectAnswers: (json['incorrect_answers'] as List)
          .map((answer) => Uri.decodeComponent(answer as String))
          .toList(),
    );
  }
  ```
- **Why `Uri.decodeComponent`**: Open Trivia DB returns HTML-escaped text by default (`&quot;`, `&#039;`, etc.). Rather than pulling in an HTML-entity-decoding package, the request asks the API for URL-encoded text instead (`encode=url3986`, Step 3) and decodes it with Dart's built-in `Uri.decodeComponent` — zero extra dependencies.

#### Step 3: Create the network service ####
- Equivalent to `ApiService.kt` + the Retrofit object + `QuizApi` singleton (Android Steps 5–6).
- New file `lib/services/quiz_service.dart`:
  ```dart
  import 'dart:convert';

  import 'package:http/http.dart' as http;
  import 'package:quiz_app/models/quiz_questions.dart';

  Future<List<QuizQuestion>> fetchQuizQuestions({
    int amount = 10,
    int category = 18,
    String difficulty = 'easy',
    String type = 'multiple',
  }) async {
    final response = await http.get(
      Uri.parse(
        'https://opentdb.com/api.php'
        '?amount=$amount&category=$category&difficulty=$difficulty&type=$type&encode=url3986',
      ),
    );

    if (response.statusCode != 200) {
      throw Exception(
        'Failed to load quiz questions (status ${response.statusCode})',
      );
    }

    final data = jsonDecode(response.body) as Map<String, dynamic>;
    final responseCode = data['response_code'] as int;
    if (responseCode != 0) {
      throw Exception('Open Trivia DB returned response_code $responseCode');
    }

    final results = data['results'] as List;
    return results
        .map((json) => QuizQuestion.fromJson(json as Map<String, dynamic>))
        .toList();
  }
  ```
- `amount = 10, category = 18, difficulty = "easy", type = "multiple"` are the same query parameters used in the Android `getQuizList()` call (Android Step 7) — `category = 18` is Open Trivia DB's "Science: Computers" category.
- A plain top-level `async` function is enough here — there's no interface/implementation split like `ApiService` + `QuizApi.retrofitService`, since Dart doesn't need Retrofit's dynamic-proxy code generation to turn a URL + query params into a typed call.

#### Step 4: Handle network and API errors ####
- Equivalent to Android's try/catch around the Retrofit call (Android Step 8) — but instead of swallowing the error and returning an empty list, `fetchQuizQuestions()` throws:
  - a status-code exception if the HTTP request itself fails (non-200),
  - a `response_code` exception if Open Trivia DB responds successfully but reports it couldn't satisfy the query (e.g. not enough questions for that category/difficulty combination).
- Throwing here (instead of catching) is intentional — it hands the error to `FutureBuilder` (Step 6), which already has a dedicated error-display path, so failures are visible instead of silently becoming an empty quiz.

#### Step 5: Network permissions ####
- No Flutter equivalent needed. Android Step 9 (`<uses-permission android:name="android.permission.INTERNET" />`) is already present by default in every `flutter create`-scaffolded Android project, and iOS doesn't require an explicit permission for plain HTTPS requests. Nothing to change here.

#### Step 6: Fetch the questions where they're needed, with `FutureBuilder` ####
- Equivalent to `QuizViewModel.getQuizList()` + `viewModelScope.launch` + the `LiveData` observer in `MainActivity` (Android Steps 7, 14–17) — but collapsed into the widget that actually needs the data, since Flutter doesn't require a separate ViewModel layer for this.
- In `lib/screen/question_screen.dart`, the fetch is kicked off once in `initState()` and stored in a `Future` field (not called directly inside `build()`, which would re-trigger the request on every rebuild):
  ```dart
  late final Future<List<QuizQuestion>> _questionsFuture;

  @override
  void initState() {
    super.initState();
    _questionsFuture = fetchQuizQuestions();
  }
  ```
- The `build()` method wraps the question UI in a `FutureBuilder`, handling all three states of the request:
  ```dart
  FutureBuilder<List<QuizQuestion>>(
    future: _questionsFuture,
    builder: (context, snapshot) {
      if (snapshot.connectionState == ConnectionState.waiting) {
        return const CircularProgressIndicator();
      }
      if (snapshot.hasError) {
        return Text('Could not load quiz questions.\n${snapshot.error}');
      }
      final questions = snapshot.data!;
      // ...render the current question using `questions`
    },
  )
  ```
- This is the same "loading / error / success" branching that `Toast.makeText(this, "List size = ${list.size}", ...)` only partially covers on the Android side (Android Step 16 shows a toast on success, but has no explicit loading or error UI).

#### Step 7: Pass the fetched list forward instead of a shared adapter dataset ####
- Equivalent to `QuizAdapter.clear()` + `addAll()` + `notifyDataSetChanged()` (Android Steps 18–20) — but Flutter doesn't need a mutable, cleared-and-refilled dataset object. Since `List<QuizQuestion>` is immutable, typed data, it's simply passed forward through widget constructors as the quiz progresses:
  - `QuestionScreen` fetches the list and keeps it in scope for the whole question flow.
  - Once every question is answered, it's forwarded to `ResultsScreen(questions: questions, selectedAnswers: selectedAnswers, ...)` via `Navigator.pushReplacement`.
  - `ResultsScreen` builds its summary directly from that list — no shared, mutable adapter state to clear and repopulate.

#### Step 8: Remove the old hardcoded question bank ####
- `lib/models/sample_question.dart` (the static, hardcoded `List<QuizQuestion>` used before this integration) was deleted, along with every import of it — the app now always sources questions from `fetchQuizQuestions()`. There's no Flutter equivalent to Android Step 19's "pass an empty list as the initial default value," since `FutureBuilder`'s waiting state already covers "nothing to show yet."

#### Step 9: Verify ####
- Equivalent to Android Step 21 ("run the app").
- `flutter analyze` — no issues.
- `flutter test` — the existing widget test (start screen + form validation) still passes unaffected by the network change.
- Ran on the iOS Simulator: submitted the name form, confirmed the loading spinner appears then resolves into real "Science: Computers" trivia questions pulled live from `https://opentdb.com/api.php`, answered through to the results screen, and confirmed Restart returns to the start screen.
